# 社团活动室预约 · 轻量产品案例

让「现在到底谁在用这间房」成为相关方都能看到、随变更同步的事实。

**在线查看**：https://qihuai823.github.io/club-room-case/

> ⚠️ **声明：3 场访谈为 AI 模拟产出，受访者原话来自真实场景。** 频次、比例等数字为口述估算，未经实测。
> 可以核验的是**方法**：访谈 → 痛点锚点 → PRD 草稿 → 硬规则门禁 → 产品判断。

**30 秒看懂**

- **问题**：学校预约系统只记「申请」，钥匙本只记「借还」，两者对不上。组织者不知道房间能不能用，场地管理者不知道现在谁在用。
- **判断**：不是再做一个预约系统，而是让占用状态有单一可信来源。状态分「计划 / 实际 / 存疑」三层，冲突只提示、不自动裁决。
- **证据规则**：每条结论绑定原话、频次和证据强度；区分「复现」（不同人各自经历）和「佐证」（多人描述同一件事），佐证不计入复现。
- **为什么 MVP 不用 AI**：痛点是数据源不一致，不是看不懂消息；用 AI 推断占用会引入新的不可靠来源。页面里写明了什么情况下才该加 AI。

## 方法

| 环节 | 做了什么 |
|---|---|
| 访谈 | 3 场 AI 模拟深访（原话取自真实场景）：高频组织者（甲）、低频组织者（乙，用来划定边界）、社联场地干事（丙，管理侧） |
| 锚点 | 把痛点拆成可复核条目，逐条绑定原话 + 频次 + 证据强度 |
| 工具 | 用自建的 PRD 工作流（硬规则门禁 H1–H10 + 软规则评分）把素材转成结构化草稿；确定性判断交给代码，语义判断交给模型 |
| 交叉验证 | 用户侧（甲）与管理侧（丙）对 4 条关键事实的描述是否一致 |

## 已知缺口

- 访谈过程是 AI 模拟的，没有现场追问；所有频次和比例都没有实测。
- 没有普通社团成员视角，三位受访者都是学生，审批侧的教职工不在样本内。
- 页面是产品判断，不是完整 PRD：还缺验收标准和上线计划。
- 下一步：找真实的社团负责人和场地管理者重做访谈，验证假设 A1–A6。
