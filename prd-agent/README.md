# AI 办公 PRD Agent（需求素材 → 结构化 PRD）

把零散、口语化、互相矛盾的需求素材（用户反馈、访谈记录、客服工单、竞品动态），转成一份**结构完整、验收标准可测量、来源可追溯**的 PRD 草稿，并在输出前用质量门禁挡住空话与幻觉。

> **仓库当前状态（先说清楚）**
> ✅ **已提供**：可运行的规则节点与自测——硬规则 **H1–H10**（`nodes/prd-hard-rule-node.py`）、自动打分节点（`nodes/prd-score-node.py`）、3 份回放样本、金标准 PRD，以及覆盖正反用例的节点自测（**20 项断言，全部通过**）。
> ⚠️ **尚未提供**：打包好的 Dify 工作流 DSL（`dsl/*.yml`）。要跑完整流水线，需按下面「架构」一节自行把两个代码节点接进 Dify。
> 这样标注是为了让「有什么、没什么」一眼可见——**读的人不必去猜**。

**30 秒看懂**

- **解决什么**：产品经理拿到的原始素材是碎片化、重复、自相矛盾的。把它整理成一份合格 PRD 需要反复归类、补写验收标准、追查来源；本流水线把「素材整理 → 需求抽取 → 优先级 → PRD 写作 → 质量门禁」串成一条可重复运行的链路。
- **怎么保证靠谱**：确定性判断交给代码节点（必填章节是否齐全、验收标准是否含可测指标、是否命中禁用空话、引用能否在素材中溯源、**判断依据是否只提竞品**、验收标准是否客观可判定、上线计划是否含灰度时长），LLM 只负责抽取、聚类与写作；PRD 规范抽成环境变量 `prd_rules`，作为抽取 / 写作 / 评审三个节点的单一事实来源。
- **两层输入**：`competitor_text`（竞品动态，直接消费 `AI-office-competitor-daily` 的结构化输出）+ `feedback_text`（用户反馈）。竞品情报回答「别人做了什么」，用户反馈回答「我们的人痛不痛」——**只有两者指向同一件事，才是一条站得住的需求**。
- **怎么证明**：3 份回放样本（真实感素材 + 边界合成样本）；评分维度见 [`docs/prd-rubric.md`](docs/prd-rubric.md)；节点自测 20 项断言全通过。
- **自己复测**：`python tests/test_nodes.py` —— **不依赖 Dify**，直接跑两个节点的自测。自动打分逻辑在 `nodes/prd-score-node.py`，样本在 `fixtures/`。

## 架构

```
开始（competitor_text 竞品动态 + feedback_text 用户反馈）
  → [代码] 素材切分与近似去重
  → [LLM] 需求条目抽取（强制结构化 JSON）
  → [代码] JSON schema 校验 + 合并重复需求
  → [LLM] 需求聚类 + 优先级判定（引用 prd_rules）
  → [LLM] 按固定章节模板生成 PRD 草稿
  → [代码] 硬规则检查（章节齐全 / 验收标准可测 / 禁用词 / 引用可追溯 / 依据不得只有竞品）
  → [LLM] 评审员按 rubric 打分
  → [代码] 解析评审结果
  → IF 通过 → 输出 ；ELSE → 重写 LLM → 回到硬规则检查
  → [Jinja] 渲染 Markdown PRD
```

**职责分离**：章节完整性、可测性、禁用词、溯源这类确定性逻辑全部下沉到代码节点；LLM 只做语义判断与写作。与 `AI-office-competitor-daily` 的架构同构——多路输入 → 抽取 → 合并定级 → 硬规则 → 评审 → 重写 → 渲染。

## 质量门禁

- **硬规则（代码判定，H1–H10）**：不通过直接打回重写，并指出具体问题。
- **软规则（LLM 按 1–5 分判定，S1–S5）**：低于 3 分打回重写。
- **通过条件**：H1–H10 全通过，且 S1–S5 均 ≥ 3 分。

完整定义见 [`docs/prd-rubric.md`](docs/prd-rubric.md)。

> **H9 / H10 / S5 来自一次外部独立评审**，三条都不是拍脑袋加的，而是暴露了**规则本身的洞**。经过记在 [`docs/error-log.md`](docs/error-log.md)。

### H8：本项目最核心的一条规则

**需求的「判断依据」不得只有竞品。**

判据是不对称的——只提竞品会被打回，**只提用户则通过**。因为「竞品有 → 我们也要有」是抄作业，而「用户有痛点 → 竞品没做」恰恰是最该做的差异化机会。若规则写成「必须提到竞品」或「提到竞品即错」，都会把正确的需求一起误杀。

## 评测方法（Harness）

- **回放评测**：回测副本跳过外部检索，把素材文本直接作为输入（`fixtures/`），同一输入可反复跑。
- **合成样本**：边界用例覆盖空素材、需求互相矛盾、单一需求、超长素材、含禁用空话素材。
- **自动打分**：`nodes/prd-score-node.py` 按样本期望检查章节、条目、优先级、过滤与禁用词，输出 `score` / `fails`。
- **停止标准**：每个样本跑 3 遍。同一问题 3 次里至少 2 次复现、并且会误导读者才修改；只出现 1 次的波动记进 [`docs/error-log.md`](docs/error-log.md)，不改。

## 结果

| 样本 | 内容 | 期望 | 结果 |
|---|---|---|---|
| F1 正例 | 竞品动态与用户反馈互相印证 | 需求 2 条，导入速度不得进清单 | 待填 |
| F2 反抄袭 | 竞品有（PPT 配图）、用户无 | 需求 1 条，配图不得进清单 | 待填 |
| F3 素材不足 | 无竞品动态 + 一条模糊反馈 | 需求 0 条，不得编造功能名 | 待填 |

> 「结果」一栏需跑**完整流水线（含 LLM 节点）**才能填。本仓库当前只提供代码节点与其自测，因此留空——**不用估算值或单次运行结果冒充**。

**已离线验证**：手写的金标准 PRD（`examples/golden-prd-F1.md`）通过全部硬规则（含 H8），对 F1 期望得 **8/8** 满分。见 `tests/test_nodes.py`。

## 已知问题

**规则层面的已知缺陷（已修，但值得记住）**

- **H3 曾经抓不住「数字外壳」**：原实现只检查验收标准「是否含数字或判定词」，于是「抽检 **100% 可读**」因为含 `100%` 而被放行——这正是本项目要防的废条。**规则声明了目标（可测量），实现只抓了表层特征（有数字）**。已新增 **H9** 兜住。
- **指标与观测方式不匹配没人管**：成功指标写「公式求助平均耗时」，观测方式填「埋点」，但求助发生在产品外，埋点测不到。原 S1–S4 都没覆盖。已新增 **S5**。
- **灰度计划没写时长**：写了范围与阈值，没写跑多久。已新增 **H10**。

**尚未解决**

- **完整流水线未端到端跑过**：LLM 节点（抽取 / 聚类 / 写作 / 评审）目前没有可回放的执行记录，因此上表「结果」为空。
- **`dsl/` 工作流未提供**：需要按「架构」一节自行在 Dify 中接线。

完整决策记录见 [`docs/error-log.md`](docs/error-log.md)。

## 使用

**当前状态**：本仓库提供的是**可运行的规则节点与自测**，不是打包好的 Dify 工作流。

1. **跑节点自测**（不依赖 Dify，推荐先跑这个）
   ```
   python tests/test_nodes.py
   ```
   20 项断言，覆盖 H1–H10 的正反用例、金标准 PRD 满分、以及打分节点的期望机制。

2. **接进 Dify**：把 `nodes/` 下两个 Python 节点分别建成代码节点，按上文「架构」串联（Dify 工作流 DSL **尚未随仓库提供**）。

3. **喂回放样本**：把 `fixtures/` 里的样本作为开始节点输入，看自动打分节点输出的 `score` / `fails`。

## 目录

- `nodes/prd-hard-rule-node.py`：硬规则检查节点（H1–H10）
- `nodes/prd-score-node.py`：自动打分节点（EXPECT + checks + score）
- `fixtures/`：回放样本
  - `fixture-F1-crosscheck.txt`：正例，情报与反馈互相印证
  - `fixture-F2-copy-risk.txt`：反抄袭，竞品有、用户无

- `templates/prd-template.md`：PRD 章节骨架
- `docs/prd-rubric.md`：PRD 质量评分维度（H1–H10 / S1–S5）
- `docs/error-log.md`：错误日志与每次修复的决策记录
- `tests/test_nodes.py`：节点自测（不依赖 Dify，直接跑 Python）
