# PRD 质量评分维度（rubric）

定义「一份合格 PRD 长什么样」。工作流的评审节点按本表打分，`nodes/prd-score-node.py` 按本表做自动检查。

本表同时是**唯一事实来源**的文档版本；Dify 环境变量 `prd_rules` 应与本表保持一致，抽取 / 写作 / 评审三个节点都引用它，避免不同节点各用一套标准。

评分分两类：

- **硬规则（代码判定，H1–H10）**：可枚举、可字符串比对。不通过直接打回重写。
- **软规则（LLM 判定，S1–S5）**：需要语义理解，按 1–5 分打分，低于 3 分打回重写。

---

## 硬规则（代码判定）

| # | 维度 | 判定方式 | 不通过的处理 |
|---|---|---|---|
| H1 | 必填章节齐全 | 输出含全部 `REQUIRED_SECTIONS` 章节标题 | 打回重写并指出缺哪节 |
| H2 | 每条需求有验收标准 | 需求清单中每条需求的「验收标准」列非空 | 标出缺验收标准的需求 |
| H3 | 验收标准可测量 | 验收标准至少含一个数字或明确判定词（≥ / ≤ / 不少于 / 不超过 / 通过 / 不通过） | 标出模糊验收标准 |
| H4 | 无禁用空话 | 不命中禁用词表（无主体、无指标的空泛表述） | 标出命中位置 |
| H5 | 引用可追溯 | 输出中带引号的关键事实（用户原话、数据）能在输入素材中找到对应字符串 | 标出无法溯源的断言 |
| H6 | 优先级取值合法 | 每条需求的优先级 ∈ {P0, P1, P2, P3} | 标出非法取值 |
| H7 | 无占位符残留 | 输出不含「待补充」「待确认」「TBD」「TODO」「XXX」「{{」 | 打回重写 |
| H8 | 需求不得仅以竞品为唯一依据 | 「判断依据」列提及竞品，但不含任何用户侧支撑（用户 / 客户 / 反馈 / 访谈 / 工单 / 痛点 / 场景 / 影响面 / 频次） | 判定为照搬竞品，打回重写 |
| H9 | 验收标准须客观可判定 | 验收标准不含主观形容词（可读 / 好用 / 易用 / 清晰 / 流畅 / 友好 / 智能 / 高效 / 美观 / 稳定 / 顺畅 / 直观 / 合理） | 标出，要求替换为可操作定义 |
| H10 | 上线计划须含灰度时长 | 「上线与验证计划」章节含明确时间窗（如 2 周 / 14 天 / 1 个月） | 标出，要求补充时长与决策时点 |

### 禁用词表（初始版本，随 error-log 迭代）

`更好的体验`、`提升效率`、`优化流程`、`加强`、`赋能`、`闭环`、`一定程度`、`尽可能`、`尽快`、`合理`

> 说明：判定标准不是「这个词本身有错」，而是「在 PRD 里出现且没有主体、没有指标 = 无法验收」。因此禁用词命中一律打回，要求改写成「谁 / 在什么场景 / 指标从 X 到 Y」。

### 关于 H8（本项目的核心规则）

这条规则来自一个具体的产品判断：**竞品情报回答「别人做了什么」，PRD 回答「我们要做什么、为什么」。两者之间隔着「产品判断」这一层，不能直连。**

如果输入只有竞品动态，模型会倾向于生成「竞品有 → 我们也要有」的需求。那不是需求，是抄作业。更糟的是，如果 rubric 不禁止，**自动打分反而会奖励抄袭**。

H8 的判据是**不对称**的，这一点必须说清楚：

| 判断依据的内容 | 是否通过 H8 | 原因 |
|---|---|---|
| 只提竞品，无用户侧支撑 | ✗ 打回 | 照搬竞品 |
| 只提用户，无竞品依据 | ✓ 通过 | **从用户问题出发是合法需求**，不要求必须有竞品参照 |
| 用户 + 竞品都有 | ✓ 通过 | 最理想：用户痛点真实，且竞品已验证方向 |
| 都没有 | ✗ 打回 | 由「缺少优先级判断依据」兜住 |

**只禁「只提竞品」，不禁「只提用户」。** 否则会把差异化机会（竞品没做但用户需要）一起杀掉——那恰恰是最该做的需求。

### 关于 H9 / H10 / S5（由外部评审发现后新增）

这三条规则来自一次外部独立评审（用 Hark 对金标准 PRD 做挑错），三条缺陷都不是随机波动，而是**规则本身的漏洞**：

| 发现的问题 | 为什么原规则挡不住 | 新增规则 |
|---|---|---|
| 验收标准写成「抽检 100% 可读」 | H3 只检查「有没有数字」，没检查「这个数字背后是否客观可判定」；「100%」给主观判断套了个数字外壳 | **H9** |
| 成功指标写「公式求助平均耗时」，观测方式却填「埋点」 | 归 S 类语义问题，原 S1–S4 都没覆盖「指标与观测方式是否匹配」 | **S5** |
| 灰度计划写了范围和阈值，没写跑多久 | 无对应规则 | **H10** |

**H9 的由来值得单独记住**：它证明了一类典型失败——**规则声明了目标（可测量），实现只抓了表层特征（有数字）**。这类漏洞不会自己暴露，只有外部评审才会戳穿。

**主观词的操作化写法**（H9 不通过时的改法）：

| 主观写法 | 操作化写法 |
|---|---|
| 解释可读 | 由 5 名目标用户独立阅读后，能正确复述公式作用的比例 ≥ 80% |
| 界面好用 | 完成主任务的操作步数 ≤ 3 步，且成功率 ≥ 90% |
| 结果清晰 | 解释须引用该公式用到的全部字段名，字段名一致率 100%（可自动校验） |

## 软规则（LLM 按 1–5 分判定）

| # | 维度 | 5 分 | 1 分 |
|---|---|---|---|
| S1 | 需求是否来自素材 | 每条需求都能指向素材来源 | 大量凭空编造 |
| S2 | 优先级是否有依据 | 每条都给了判断依据（频次 / 影响面 / 实现成本） | 拍脑袋排序 |
| S3 | 表述是否无歧义 | 研发可直接开工 | 需要大量澄清 |
| S4 | 场景描述是否完整 | 含目标用户 + 使用场景 + 当前痛点 + 期望结果 | 只有功能罗列 |
| S5 | 指标与观测方式是否匹配 | 每个成功指标的观测方式真能测到该指标 | 声称埋点，但指标发生在产品外（如线下求助），实际测不到 |

---

## 通过条件

**H1–H10 全部通过，且 S1–S5 均 ≥ 3 分。**

任一不满足 → 进入重写分支，并把 `hard_issues` 与低分维度一并作为重写提示词输入。

---

## 为什么这样分

- **能用代码判的绝不给 LLM**：LLM 判「章节齐不齐」「有没有数字」既浪费 token 又不稳定，同一输入两次结果可能不同。
- **LLM 只判需要理解的东西**：需求有没有依据、表述有没有歧义，这类判断代码做不了。
- **每一条规则都要能落到一句话**：说不清的规则就是不存在的规则，评审节点也没法稳定执行。
